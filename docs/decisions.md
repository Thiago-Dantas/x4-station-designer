# Decisions

## Decided
| ID | Date | Decision | Why |
|----|------|----------|-----|
| D-1 | 2026-10-13 | Project state lives in `.md` files (`tasks/`, `docs/`), not in session history | This is a long-term project that runs over many sessions |
| D-2 | 2026-10-13 | The game install and the player profile are read-only by default; profile writes need a backup first | Protect the user's game and saved plans |
| D-3 | 2026-10-13 | Git, hosted as a private GitHub repo | User decision (was OD-4) |
| D-4 | 2026-10-13 | Use REA on `X4.exe` to answer whether plan `offset` is authoritative or recomputed from connections | User decision. **Settled without REA** the same day by in-game test C: the offset is authoritative. REA stays available for later questions. |
| D-5 | 2026-10-13 | **Primary injection route = option B**: the tool writes a single-plan file into `<profile>\constructionplan\`, and the player uses Import in the build menu | User decision (was OD-3). Verified in game: vanilla, no restart, never touches `constructionplans.xml`. Option D (a live mod) stays a later add-on. |
| D-6 | 2026-10-13 | **Rust + Tauri.** The core library, CLI and MCP server (official Rust SDK) are in Rust. The visual builder is a web UI (Three.js for 3D) inside Windows' built-in WebView2, bundled into one exe. | User decision (was OD-2; replaces a short-lived TypeScript pick). Meets the requirements: a compiled, self-contained exe of about 10 MB, fast, with nothing for users to install. WebView2 ships with Windows 10/11 (v155 on the dev machine). The snap math lives once in Rust and can be compiled to WASM for drag-time snapping in the UI. The Python scripts in `tools/` and `research/` stay as reference implementations. |
| D-7 | 2026-10-13 | **Live link between builder and agents.** The builder app is the hub. An agent's MCP process (its own copy of the exe) connects to the running builder over a local socket and edits the open design, so changes show up live and the user can drag alongside. Without a running builder, the MCP process works on design files headless. | User decision (was OD-6). |
| D-8 | 2026-10-13 | **Both MCP and CLI from one exe:** `x4sd` opens the builder, `x4sd mcp` serves MCP over stdio, `x4sd <command>` for scripts. All call the same core functions. | User decision (was OD-1). |
| D-9 | 2026-10-13 | **Overlap rule:** modules overlap when boxes built from their collision meshes intersect by more than 1 m, unless they are joined at a snap. Auto-placement never creates such overlaps; `validate` reports them. | Made while building auto-placement (part C) and calibrated on the player's and the game's own plans (docs/x4-construction-plans.md, "Overlaps"). The checklist's assumption (part boxes shrunk by a few metres) failed: part boxes give false overlaps up to 491 m, and joints interlock by design (up to 130 m). **Refined 2026-10-14** (user report: TerranScrapyard, built in game, showed 6 overlaps): `validate` confirms box overlaps on the collision-mesh triangles, so the player's plans show none. Auto-placement keeps the stricter box test. |
| D-10 | 2026-10-14 | **Equipment** is edited per group (as plans store it), and in bulk three ways: picks per kind and size, loadout level presets, and copying a module's equipment to its type or to all modules. Bulk equipping covers every module with groups by default, or defence modules only. | User decision. The loadout level is our own rule (see docs/x4-construction-plans.md, "Equipment"). |
| D-11 | 2026-10-14 | **A renamed plan becomes a new plan.** Before Export or Save as, if the player's saved plans or import files have the plan's id under another name, the plan gets a new id. In game it then imports next to the original. | User decision. With the id kept, the game listed the renamed file as already imported, and Import would have replaced the original. |
| D-12 | 2026-10-14 | **Clearance rule:** each exclusion zone (`exclusionzone ship_<class>` on piers, bays, dock areas…) is a box of the `parameters.xml` size (full widths), from its connection along +Z for its whole length (100 km for L/XL). A module blocks it when one of its collision boxes reaches more than 1 m inside, unless it is the zone's own module or joined to it at a snap. `validate` reports it as a problem; auto-placement and Optimize keep every zone clear, both ends of L/XL bays included. | User decision on the options from the research (docs/x4-construction-plans.md, "Clearance: exclusion zones"): this box fits the user's game-built plans (the only intrusions are joined back-to-back piers) and nearly all library plans. |
| D-13 | 2026-10-14 | **In-game load = counts, not a score.** The readout shows module, connection-structure, turret, shield and dock counts and the size; it doesn't combine them. *Fewer connection structures* is an option (off by default) that raises the hub threshold from 2 to 4 km. | User asked for both after the FPS question. Nothing about frame rate is measured, so a combined score would be made up. The option trades connectors for size, and sprawl is a load too, so it stays a choice (docs/x4-construction-plans.md, "Auto-placement"). |
| D-14 | 2026-10-14 | **Optimize shows a plan first.** Optimize station lists the shortfall fixes; *Buy* on a chain row buys the ware and re-plans (its feeders drop out), ✕ on other rows leaves them out; *Apply plan* runs it. Afterwards the plot is fitted exactly to the station, with no prompt (also for MCP `optimize_station`). | User decisions (Buy-and-re-plan over plain row removal or count editing; exact fit over grow-only). |
| D-15 | 2026-10-14 | **Planner extras.** The planner takes other modules (with a count; in the builder only defence, storage and ship-building modules, user request 2026-10-14, since production comes from the ware box; piers and dock areas too, and only the planner race's modules plus universal ones (no race), user requests 2026-10-15) and storage minimums per cargo type. Storage per type = the larger of the minimum and the hours rule, made of the largest module plus the smallest that covers the rest. Defence platforms take sides of the station (count spread evenly over the sides picked); auto-placement puts them last, on the outside of that side with nothing in front of them (a clear lane), and reports those it couldn't. Ship bays add only the bays and their workforce, not the wares ships are built from. | User decisions on the four options offered (all as recommended): side of the station, not the disc's own tilt; count + sides, not a count per side; bays + workforce; minimums on top of storage hours. The lane rule is ours (workflow-planner-extras.md). |
| D-16 | 2026-10-14 | **Blueprint limit from a save.** An option, off by default, reads the player's blueprint list from a save they pick. While it is on, the palette, MCP `list_modules`, and the modules the planner, *Place all* and Optimize choose (including connection structures) are limited to modules with a blueprint. Modules named explicitly (planner extras, explicit module lists, attach) are still used. Wares that only modules without a blueprint make are reported (`no_blueprint`). The list is cached: turning the option on again doesn't re-read the save; *Other save…* and *Re-read* do. The builder remembers the option and the list (localStorage) and hands them to its core at start. MCP gets `read_blueprints` (default: the newest save) and `blueprint_filter`. | User request and decisions (scope: palette, planner and MCP; remembered across restarts). It is opt-in because a save is ~1 GB of XML; the reader stops after the list (0.4 s). The game's build menu also offers only blueprinted modules (docs/x4-game-data.md, "Savegames"). |
| D-17 | 2026-10-14 | **No code, data or text from x4ep_planner.** The planner, station analysis, auto-placement and Optimize are our own, written from the game files (`wares.xml`, module macros and components, `parameters.xml`). The mod was studied in Phase 1 only for which game APIs it calls (docs/x4-plan-apis.md) and for what its features do (its readme). Its Lua, data tables and wording are not copied or ported. | The mod's licence asks for permission before its code is reused. **Audit 2026-10-14 (verified):** none of the mod's identifiers or constants occur in our code; our planner shares none of its concepts (tiers, delivery bands, scoring); our placement works on snap geometry, while the mod hands a module list to the game's generator; its sunlight factor is `effect × sunlight`, ours `1 + (sunlight − 1) × effect`. A word-sequence comparison (`8`- and `6`-word runs, ~140,000 from the mod's Lua, MD and text files, against our Rust, TypeScript, HTML and docs) found one near-verbatim phrase, the storage-hours tooltip ("this many hours of everything the station makes and uses"), now reworded; the rest were plain English or file-format boilerplate. Shared by design, not copied: the feature set the user asked for (plan, Optimize, place), the 6-hour storage default, and formulas that follow from the game data (output × (1 + work × workforce fill)). Not a clean room in the strict sense: the same author read the mod's Lua during research. |
| D-18 | 2026-10-14 | **Adding modules never moves the station's own.** *Place all* (and MCP `auto_place`) no longer lifts the station's dock areas, piers and bays to place them again outside; their corridors and zones are protected where they stand. In the builder, Optimize's *Apply plan* only adds the modules unless *Rebuild connection structures* is on (then: full re-layout in layers). The builder no longer uses the keep-the-shape re-layout; MCP `optimize_station` keeps `keep_shape`. | User report: "generate a plan and apply" changed the station's layout with neither box ticked. User choices: Rebuild off = only add; leave existing docks in place. |
| D-19 | 2026-10-14 | **New-version notice.** The builder asks the GitHub API for the latest release once per start (from the UI; no updater, no download). A newer release than the running version, and than the last one skipped, shows a bar: *Download* opens the release page (`tauri-plugin-opener`), *Skip this version* remembers the tag (`localStorage` `x4sd.skipVersion`). Any later release shows it again. CLI and MCP don't check. | User request ("notify", "if a user doesn't want 1.1, notify again at 1.2"). Open page rather than self-update: the exe is unsigned and has no installer. |
| D-20 | 2026-10-15 | **Copy and remove like the game.** A *sequence* is a module with everything attached to it (its subtree). In the builder, *Remove* (Del) removes the module alone: what was attached to it stays where it is, unattached, and *Checks* reports it until it is re-attached (*Move…*). *Remove sequence* (Shift+Del) is the old Remove. *Copy* (Ctrl+C or middle click) arms the module's type; *Copy sequence* (Ctrl+Shift+C or Shift+middle click) puts copies of the sequence, with equipment and without stage ends, onto each free snap clicked, at the end of the build order. The *not attached* check skips the first module in the build order and modules that meet another at a snap. MCP `remove_module` still removes a sequence. | User request. The check's snap exception comes from the game's own plans: 43 of the 58 unlinked modules (not first) in the library and the player's plans meet another module at a snap (docs/x4-construction-plans.md); flagging them would be false alarms. |
| D-21 | 2026-10-15 | **Place all asks before a partial build** (user request). When some modules find no place, the builder asks; *No* undoes the placement, *Yes* keeps it and the plan drops what was placed. Optimize stays all or nothing. Placement tries chains of struts before it gives up ("reach"). | A silent partial placement left the plan and the station out of step, and the user had no say. |
| D-22 | 2026-10-15 | **Breaking the station up** (user: "when Rebuild connection structures is OFF we should only [move modules] when nothing fits otherwise, when ON dont even think too much and just move stuff around and add connectors where it makes sense"). Off: placement may move the station's modules (a hub into a joint) only when a module finds no place otherwise; this narrows D-18. On: *Place all* (not only Apply plan) lays the whole station out again with the new modules. Optimize may keep a partial result, but only added modules may stay out. Undoing a Place all gives its plan items back, added to the plan. | Sealed stations (every free snap facing a neighbour) could take nothing more. |
| D-23 | 2026-10-15 | **Defence platforms and piers outermost.** Defence modules (class `defencemodule`: disc and bridge platforms, Administrative Centres) join dock areas, piers and bays in the outer layer, and dock areas, piers and defence modules all need the 3 km corridor out from the station's centre (nothing further out on that line). Applies to *Place all* and Optimize. Modules placed on a chosen side keep their side lane instead. | User report: Optimize put a Terran Disc Defence Platform deep inside a station; "large piers and defense modules should always be on the outermost". Costs more connection structures (docs/x4-construction-plans.md, *Docks stay reachable*). |
| D-24 | 2026-10-15 | **Finding the game on any machine.** Lookup order: `--game-dir`, `X4_GAME_DIR`, the folder picked in the builder, every Steam library (Steam's folder from the registry), GOG installs (registry). A folder counts only with `01.cat`. When the builder finds none, it asks for the folder (folder dialog, asked again on a wrong pick) and saves it in `%APPDATA%\x4sd\game-dir.txt`, which the CLI, MCP server and the game-data tests read too. The MCP server looks again when it first loads the game data. | User request: the game path was only right on the dev machine (the hardcoded path was in tests and research tools; the app only searched the default Steam folder) and a player who double-clicks the exe can't pass `--game-dir`. Scope chosen by the user. Details in docs/x4-game-data.md. |
